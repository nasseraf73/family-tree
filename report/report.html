١ الملخص التنفيذي

فحص شامل لكود src/ و drizzle/ في مشروع FamilyTree Al-Nammari (Next.js 14 + Drizzle ORM + PostgreSQL عبر Supabase Pooler). كل مشكلة في هذا التقرير مرفقة بـ file:line فعلي من الكود الحالي، ولا توجد أي تكهّنات أو تقديرات غير مبنية على قراءة الكود.

التوصية المرحلية

خطة من ٦ مراحل متسلسلة، تبدأ بتغييرات صغيرة منخفضة المخاطر (يوم واحد) وتنتهي بإعادة هيكلة معمارية (أسبوعان). المرحلة الأولى وحدها تضيف ٣٠–٥٠٪ من التحسين، والمراحل مجتمعة تضيف أكثر من ٩٠٪. كل مرحلة لها معايير نجاح قابلة للقياس.

٤ السيناريو الأول: ٥٠–١٠٠ مستخدم متزامن

هذا السيناريو يفترض أن ٥٠ إلى ١٠٠ مستخدم يدخلون النظام في وقت واحد (مثل حملة إعلانية، إشعار بريد جماعي، أو نشر على وسائل التواصل). الفحص يكشف أن نقطة الانهيار موجودة في الكود الحالي، ولا تحتاج تجارب ضغط لتأكيدها.

التأثير الفعلي

عند ١٠٠ طلب متزامن لـ /api/v1/tree/canvas، الطلبات من ٦ إلى ١٠٠ تنتظر في طابور للحصول على اتصال. كل طلب يقرأ ٣ جداول (persons + relationships + marriages) أي ٣ round-trips للـ DB.

١٠٠ طلب × ٣ round-trips ÷ ٥ اتصالات = ٦٠+ ثانية في أسوأ الحالات، قبل حساب وقت المعالجة في Node.js نفسه.

التوصية
زيادة max إلى ٢٠ مع تحديد prepare: false (مهم مع Supabase Transaction-mode Pooler). الحساب: VPS ٤GB يستهلك ~٥٠٠MB للـ Node، يبقى ~٣GB ⇒ ٢٠ اتصال × ١٠MB = ٢٠٠MB مريح.

// السطور 50-54 — الإعداد الحالي

  await db.update(personsTable)

التأثير الفعلي

  • الـ UPDATE بدون LIMIT يطابق كل السجلات التي تبدأ بـ data:.
  • يحدث عند كل طلب قراءة للشجرة.
  • عند ١٠٠ طلب متزامن: ١٠٠ عملية UPDATE تنافس على نفس الجدول.
  • لا يوجد فهرس على photo_url ⇒ Full Table Scan + Row-level Lock لكل صف.
التوصية
احذف الكود بالكامل من داخل الـ route، وانقله إلى:
  • Migration مرة واحدة: ALTER TABLE persons ADD CONSTRAINT ... CHECK (photo_url IS NULL OR photo_url !~ '^data:')
  • أو cron يومي: 0 3 * * * ينفّذ نفس الـ UPDATE مرة واحدة.

٥ السيناريو الثاني: ٢٠ ألف سجل في الشجرة

ما يحدث فعليًا عند إضافة شخص واحد

  1. تحميل كل الـ persons والـ relationships من DB.
  2. تنفيذ findPotentialDuplicates على كل صف.
  3. كل صف يُستدعى له calculateDeduplicationScore ٤ مرات (first, father, grand, family).
  4. كل استدعاء Levenshtein يُنشئ مصفوفة ٢D.

المجموع على ٢٠ ألف سجل: ٤ مقارنات × ٢٠ ألف شخص = ٨٠ ألف استدعاء Levenshtein عند كل إضافة شخص. كل استدعاء يُنشئ ٢٥-١٠٠ object/array ⇒ ضغط كبير على GC.

التقدير الزمني
وقت POST /api/v1/persons عند ٢٠ ألف سجل: من ٥ إلى ١٥ ثانية، عند كل إضافة شخص. تجربة المستخدم: سيئة جدًا.

٥.٣ خوارزميات JS بتعقيد O(N²)

المشكلة ٣: Array.shift() و includes() في خوارزميات BFS

عالي
المواقع المتأثرة:
src/lib/kinship.ts:55, 81 · src/lib/layout.ts:148 · src/lib/treeFilter.ts:118, 143, 205, 345, 375 · src/components/FamilyTreeCanvas.tsx:239 
// النمط المتكرر في كل BFS:
while (queue.length > 0) {
  const current = queue.shift()!;  // ⚠️ O(N) per shift
  // ...
}

// + result.includes(...) - O(N) per check
if (!result.includes(resolved.parentId)) result.push(resolved.parentId);

التعقيد الفعلي

detectCircularLoop في kinship.ts:101-132 يقرأ كل العلاقات M في كل تكرار. مع ٢٠ ألف شخص و ٤٠ ألف علاقة: فحص دورة نسبية واحدة = ١٠-٣٠ ثانية CPU. يحدث عند كل إضافة شخص (في persons/route.ts:412-419).

البديل
// استبدال shift() بمؤشر
let head = 0;
while (head < queue.length) {
  const current = queue[head++];  // O(1)
}

// استبدال includes بـ Set.has
const seen = new Set();
if (!seen.has(resolved.parentId)) {
  seen.add(resolved.parentId);
  result.push(resolved.parentId);
}

WITH RECURSIVE descendants AS (
  SELECT person_id, related_person_id
  FROM relationships
  WHERE person_id = $1 AND relationship_type = 'PARENT'
  UNION ALL
  SELECT r.person_id, r.related_person_id
  FROM relationships r
  INNER JOIN descendants d ON r.person_id = d.related_person_id

CREATE MATERIALIZED VIEW mv_tree_full AS
SELECT p.id, p.first_name, p.father_name, p.grand_father_name, p.family_name,
       p.gender, p.birth_year, p.is_alive, p.is_placeholder,
       r.id as rel_id, r.person_id, r.related_person_id,
       r.relationship_type, r.status as rel_status
FROM persons p
LEFT JOIN relationships r
  ON (r.person_id = p.id OR r.related_person_id = p.id)
  AND r.status IN ('VERIFIED', 'PENDING')
WHERE p.id IN (
  SELECT DISTINCT person_id FROM relationships
  UNION SELECT DISTINCT related_person_id FROM relationships
);

٨ الخلاصة والتوصيات

الحكم المعماري

التطبيق FamilyTree Al-Nammari مبني بأسلوب وظيفي مقبول في فئته (Next.js + Drizzle + Supabase)، لكن الفحص يكشف أنه يحتوي على ١٣ نمطًا معماريًا ضارًا بالأداء، بعضها يصل إلى درجة كارثية عند الحجم المستهدف. النماذج الإشكالية ليست أخطاءً منعزلة، بل هي اختيارات تصميمية متكررة (تحميل الجداول كاملة، خوارزميات O(N²) في JS، عدم وجود فهارس).

المسارات المقترحة للبدء

الخيار ١ — موصى به · P0 + P1 فورًا

يومين عمل فقط، تأثير كبير، مخاطرة صفر. يزيل ٣ round-trips من كل طلب قراءة، ويضاعف سرعة كل استعلام DB.

الخيار ٢ — P2 + P3 معًا

أسبوعان، مناسب إذا عندك deadline قريب للمنتج. يجلب الحل الجذري لـ DB.

الخيار ٣ — P3 ثم P2

ثلاثة أسابيع، مناسب إذا الـ DAU المتوقع ضخم جدًا (آلاف متزامنين) وتريد الحل الجذري للـ DB أولاً قبل أي تحسينات أخرى.

مبادئ الإصلاح

  1. قِس قبل أن تُصلح: كل مرحلة لها معيار نجاح قابل للقياس. لا تحتفظ بتغيير لم يُحسّن الأرقام.
  2. غيّر شيء واحد في كل مرة: إذا اشتغلت ٣ تحسينات معًا، لن تستطيع أن تعرف أيها أفاد.
  3. سجّل المحاولات الفاشلة: التعديلات المُرجَعة تترك أثرًا في الـ git history — اجعلها في PERF.md لتفادي تكرارها.
  4. حافظ على الصحة الوظيفية: الـ "تحسين" الذي يربح بتخطي validation هو regression، ليس إنجاز.

ما لا يجب فعله

  • لا تضف React.memo في كل مكان — تكرار النمط بدون قياس يُضيف تعقيدًا بدون ربح.
  • لا تبدأ بـ P3 قبل P0+P1 — الخوارزميات المتقدمة بدون فهارس = بطء مختلف فقط.
  • لا تستخدم Drizzle migrations CONCURRENTLY داخل transaction — سيفشل بصمت.
  • لا تفترض أن force-dynamic في route.ts:8 ضروري للأمان — نُقِله في P2.
